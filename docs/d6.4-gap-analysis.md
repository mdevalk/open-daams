# D6.4 v0.5 — gap analysis (spec vs open-daams)

_Snapshot date: 2026-08-17 (previous snapshot: 2026-08-12; §9.3/§13 updated 2026-08-17 — the
Annex 9 §6.8 "authorised persons" entry on the digital permit document now carries a role
(RESEARCHER, auto-derived from the application, vs OUTPUT_CONTROLLER, HDAB-selected, per D6.3's
four-eyes principle on SPE output) and a W3C DID-shaped sample identity, all part of the signed
canonical payload; each granted dataset now also carries a `StorageLocation` (a `urn:objectstore:`
reference + a sample write-access DID) instructing the data holder where and with what identity to
upload its data — also signed. Both are fixed at issuance and, as of this snapshot, re-selectable
*only* when an amendment is approved, never added/changed ad hoc on an existing permit version — a
tightening of R9.3.x's version-integrity model, not a new capability. See §9.3 and §13 below;
previous corrections: §7 2026-08-14 — R7.3.2/R7.4.2's MAY gap closed, purpose and anonymisation
level are now frozen onto the permit alongside the data categories/conditions-of-access/safeguards
that were already there, all exported in the signed digital-permit document; coverage table also
corrected 2026-08-14 — Status now requires 100% MUST for a checkmark (§7/§9.3/§9.4 revised to ◑),
MAY- and SHOULD-coverage columns added, and a fresh check against the spec text found §13 (R13.0.1
already fully met, not just partially) and §9.1 (decision IDs and negative-decision documents
already implemented, contrary to the old text) both stale — both corrected)._

A complete gap analysis between **TEHDAS2 D6.4 — DAAMS Technical specification, v0.5 (24 March
2026)** and the current open-daams implementation, section by section. open-daams was originally
built against v0.4 (17 Sept 2025); §7 below records what v0.5 changed, but the focus of this
document is the **total gap versus the current spec**, not just the version delta.

This is TEHDAS2 D6.4-requirement-focused; the plain-EHDS-Regulation-only view is in
[`ehds-gap-analysis.md`](./ehds-gap-analysis.md), the per-article EHDS map is in
[`ehds-article-map.md`](./ehds-article-map.md), and the status tables are in
[`d6.4-status-model.md`](./d6.4-status-model.md).

> **Legend:** ✅ implemented · ◑ partial or simulated · ✗ not implemented · ⏳ blocked on an
> external dependency · — out of DAAMS scope. This is an unofficial community project; nothing
> here is compliance advice.

**Methodology:** every MUST requirement in the section counted once (✅=1, ◑=0.5, ✗=0), simple
average — not effort- or severity-weighted. §11 and §12's requirements are MAY (§12's one
MUST-bundle, R12.0.2, only applies *if* a TDH GUI is built at all, which it isn't) — excluded from
the MUST tally rather than counted as failures. §6's 34 MUST requirements are excluded on the same
basis, but for a scope reason rather than a severity one: §6 (the applicant front office) is the
central platform's / WP6's responsibility, not the back-office DAAMS this project implements — see
CLAUDE.md's scope note. §10's R10.0.1 ("Member States MUST create national procedures enabling data
applicants to appeal decisions") is excluded from that section's tally on the same basis — it's a
member-state legal/organisational obligation, not something a DAAMS codebase implements or can be
scored against; §10's denominator is 3, not the 4 an earlier snapshot of this doc used. A meaningful
share of the remaining misses are **externally blocked**, not
app gaps: the Art. 70 templates don't exist yet, and most of §14 requires a real HealthData@EU/NCP
deployment to test against, which no community implementation can build alone.

**Status column:** ✅ requires MUST coverage at 100% (a section can't show a checkmark on a
partial MUST score, however small the remaining gap); ◑ covers everything else that's at least
partially built; ✗ is nothing built; — is out of scope. **SHOULD and MAY coverage** are scored the
same way as MUST (✅-equivalent=1, ◑-equivalent=0.5, ✗-equivalent=0) but counted separately, and
only for requirements the section text explicitly marks SHOULD/MAY. "n/a" means the section has no
SHOULD/MAY requirements to score (or none have been checked against the primary spec text yet), not
that they're unmet — §8 and §9.1/§9.2 were freshly re-verified against the D6.4 PDF this pass
(along with §13, verified against the code that implements R13.0.1/R13.0.2), and §7/§10 in earlier
passes; the "n/a" SHOULD/MAY cells elsewhere reflect that those sections haven't had the same fresh
check, not a claim that they have no SHOULD/MAY requirements at all.

## 2. Section-by-section gap

### §6 — Front office (applicant): out of DAAMS scope
D6.4 §6 defines the **applicant-facing front office** — submission UI, applicant portal/login,
document upload, notifications, and dataset browsing/selection. Per this project's own scope (see
CLAUDE.md), that's the **central platform's / WP6's** responsibility, not the back-office DAAMS
open-daams implements — so §6's 34 MUST requirements are excluded from the coverage tally above,
on the same basis as §11/§12's MAY exclusion, just for a scope reason rather than a severity one.

open-daams still ships a staff-facing application form, list, submit/withdraw, and fee estimate as
a practical stand-in so the back-office workflow can be demoed end-to-end — but this is a
convenience shim, not an implementation evaluated against R6.x: there's no applicant login/portal
(an "acting as" role switcher stands in), no document upload (`Document` stays a metadata stub),
no applicant-facing notifications, no draft editing/clone/print/import, and datasets are
free-typed rather than picked from a real catalogue. The **catalogue itself** (Art. 77–80 /
HealthDCAT-AP) and dataset **selection** against it (R6.2.2–6.2.4) are likewise central-platform /
WP6 work; open-daams receives applications with datasets already chosen.

### §7 — Back office (processing): ◑ mostly implemented
Present: role-gated access (R7.1.1, as RBAC), pre-screening completeness check stored as a
structured result (`CompletenessCheck`; R7.2.1–7.2.7), assessment with decision summary + notes +
ethical review (R7.3/7.4), request/receive additional information with deadline void/recalc
(R7.5), and application status updates (R7.6; see `d6.4-status-model.md`). R7.3.2/R7.4.2 (MAY —
structured storage of the decision's elements: purpose, conditions of access, safeguards, data
categories/anonymisation level, for future reporting/publication under Art. 58(1)/57(1)(j)) is
also met: data categories (`GrantedDataset`), conditions of access (`validFrom`/`validUntil`) and
safeguards (SPE assignment) were already frozen onto the permit at issuance; purpose
(`purposeCategory`/`purposeCategories`) and anonymisation level (`electronicHealthDataFormat`) are
now frozen there too, and all of it is part of the exportable digital-permit document
(`GET /api/permits/[id]/json`, `buildDigitalPermitDocument` in
[permit-signing.ts](../src/lib/permit-signing.ts)).

Gaps:
- **Application flagging + "Restricted Mode"** for sensitive cases (R7.2.8–7.2.10).
- **Multi-country assessment** coordination for HealthData@EU applications (R7.3.6).

### §8 — Setting due dates: ◑ partial (81%, 6.5/8; SHOULD 100%, 2/2)
Present: deadline computed from the submission timestamp with both Art. 68 tracks
(`DecisionTrack` STANDARD/EXPEDITED), recalculated after both additional-info events and an
assessment extension, a required written justification when extending (R8.0.1, 8.0.6, 8.0.8),
HD@EU-imported applications now anchoring their deadline to this national DAAMS's own import time
rather than the sending country's transmission timestamp (R8.0.7 — `src/lib/hdeu.ts`, the original
`transmissionTimestamp` preserved separately on the new `hdeuTransmittedAt` field), and a simulated
transmission record for the extension justification (R8.0.9 — an `AuditLog` entry plus an in-context
note on `DeadlineExtensionPanel.tsx`, mirroring how HD@EU/NCP integrations are already documented as
simulated shells rather than real notification infrastructure). Both SHOULD items are also met: the
in-app aggregate due/overdue badge (`layout.tsx`) both notifies assessment personnel of upcoming due
dates (R8.0.5) and surfaces overdue cases for follow-up (R8.0.10) — scored separately from the MUST
tally above, per this doc's SHOULD/MAY-exclusion methodology.

Partial:
- **R8.0.2** — STANDARD/EXPEDITED tracks are real, but the spec also calls out a distinct "trusted
  health data Holder procedure" deadline path, which doesn't exist anywhere in `workflow.ts`.

Gaps:
- **No configurable internal timelines** or staff-initiated routing of an already-submitted
  application onto the accelerated track (R8.0.3, 8.0.4) — `decisionTrack` is only ever set once,
  at creation.

### §9 — Issuing a decision & permit lifecycle: mixed
- **§9.1 Generating/storing decisions — ◑ (75%, 3/4) — corrected 2026-08-14, was 38%.** R9.1.1 (HDAB
  can issue a formal decision) is met — that's the core of the whole decision workflow. R9.1.3
  ("signed, time-stamped document") is also met: positive decisions get a real signed permit
  document — the 10-section permit PDF is Ed25519-signed on issuance and re-signed on every new
  version ([permit-signing.ts](../src/lib/permit-signing.ts)), persisted and regenerated whenever
  its content changes ([permit-pdf-store.ts](../src/lib/permit-pdf-store.ts)), and independently
  verifiable against `/.well-known/jwks.json`; the signed payload also carries `grantedDatasets`
  (name + URL, grouped by data holder), so the signature attests to *what* was granted, not just
  the permit's identity and validity window. **R9.1.4 (distinct decision ID linked to the
  application) is also met, correcting an earlier stale claim in this doc**: the `DECISION_ISSUED`
  transition ([transition/route.ts](../src/app/api/applications/[id]/transition/route.ts))
  generates and persists a `decisionId` (e.g. `DEC-NL-2026-0001`) on `Application` for *every*
  decision, positive or negative — the doc previously said "no code populates it," which was true
  when first written but not since the §9.2 decision-card work landed; **negative decisions also
  already get a real signed document** (see §9.2 below), correcting this doc's other stale claim
  that they get "no document at all." Only remaining gap: **Art. 70 Commission templates**
  (R9.1.2, blocked — see §5).
- **§9.2 Decision cards / decisions pending acceptance — ◑ (63%, 2.5/4; SHOULD 83%, 2.5/3; MAY
  0%, 0/2).** A *decision card* is a **structured message/record format** (not a UI element) in
  which the decision is communicated over the HealthData@EU interface; a positive decision is
  issued as an unsigned **pre-permit** for the applicant to review, a negative one as a signed
  decision PDF, and the applicant replies Accept/Reject/Appeal (R9.2.1–9.2.4, all MUST). New in
  v0.5, for **national** applications too (R9.2.5, SHOULD) with the same **28-day** response window
  (R9.2.6, SHOULD): the `DECISION_ISSUED` transition
  ([transition/route.ts](../src/app/api/applications/[id]/transition/route.ts)) generates a
  `decisionId`, renders the decision-card PDF (`generate-decision-pdf.ts`), signs it for negative
  outcomes (`signDecisionCard`), and for positive outcomes sets `permitConditionsSentAt` /
  `permitAcceptanceDeadline` (28 days) / `permitAcceptanceStatus: PENDING`. A new
  `PATCH /api/applications/[id]/decision-card` endpoint lets the applicant Accept/Decline
  (`DecisionCardPanel.tsx`, role-gated to APPLICANT for self-service), gating `PermitPanel`'s
  real-permit issuance on `permitAcceptanceStatus === 'ACCEPTED'`. Three items still unmet, and
  worth distinguishing since the spec gives them different severities: **auto-withdraw on no
  response** (R9.2.8, SHOULD) is only partially met — the 28-day deadline is surfaced as an overdue
  dashboard item and completed by an explicit staff action (`status: 'DECLINED'` on the same
  endpoint), the same lazy, non-cron pattern already used for the equally-unimplemented-as-cron
  4-week `AWAITING_ADDITIONAL_INFORMATION` no-response case, not a background job that flips the
  status on its own; **reminders during the response window** (R9.2.7, MAY) and **a withdrawal
  confirmation to the applicant** (R9.2.9, MAY) are both fully unmet — no notification system
  exists anywhere in the app.
- **§9.3 Data permit lifecycle — ◑.** Implemented as a two-axis model: `DataPermitStatus` (5
  permit statuses) + a separate `PermitChangeRequest` (workflow); see `d6.4-status-model.md`. The
  core transition logic is solid: role-gated status changes (R9.3.5), a `DataPermitLog` entry on
  every transition (R9.3.2), and a new signable version + fresh ID on approval (R9.3.6/9.3.7).
  R9.3.6's "generating the up-to-date permit version for signature" is a real, persisted, signed
  document, kept in sync with every mutation that affects it. Version archiving is via the
  `previousPermitId` chain, and the permit detail page ([permits/[id]/page.tsx](../src/app/[locale]/permits/[id]/page.tsx))
  queries every `DataPermit` row sharing the application's id to render a full version history
  (**R9.3.4 all-versions view — correcting a previous mis-assessment in this doc**: it already
  existed, and was mistakenly conflated with a separate one-hop `previousPermit` reference on the
  *application* detail page). The `DP-NL-2025-0001-v2` permit-ID format satisfies all four R9.3.8
  properties (issuing-HDAB identifier, persistent base id, version linkage, chronological
  ordering) — the spec leaves the exact string format to the Member State. Soft spot: `NL` is a
  country code, not a distinct HDAB id, so it would need extending if NL ever ran more than one
  HDAB. **R9.3.9 (delayed effective date for amendments)** is now built: approving an amendment
  with a future effective date creates the new version but keeps it `isCurrent: false` (and SPE
  provisioning re-pointed to it deferred) until a staff member activates it via
  `POST /api/permits/[id]/activate` once the date is due — surfaced as an overdue dashboard item in
  the meantime, the same lazy pattern already used for every other deadline in this app. Renewals
  and revocation appeals stay immediate, per spec.

  The Annex 9 §6.8 "persons authorised to process the data" entry on the digital permit document
  now distinguishes two roles rather than a flat list: **RESEARCHER** (auto-derived from the
  application's own `personResearchName`/`personResponsibleName`, so it's never staff-entered) and
  **OUTPUT_CONTROLLER** (selected by HDAB staff at issuance — can be HDAB staff, a data holder's
  employee, or an external expert — implementing the four-eyes check on SPE output that D6.3
  describes). Both carry a sample W3C DID-shaped identity (`src/lib/did.ts` — syntactically
  `did:key:z...`, not backed by a real keypair, same "tracked reference, not a real integration"
  posture as `SpeProvisioningOrder.environmentReference`) and only organisation + identity, never
  the individual's name — the name stays in `AuthorizedPerson`'s own DB row for HDAB's internal
  case management, never on the printed/signed document itself. Each `GrantedDataset` also now
  carries a `StorageLocation` — a `urn:objectstore:bucket:`
  reference plus its own sample write-access DID — instructing the data holder where, and with what
  identity, to upload that dataset's data. All of it (roles, identities, storage locations) is part
  of the signed canonical payload (`SignablePermit`, `canonicalPermitPayload` in
  [permit-signing.ts](../src/lib/permit-signing.ts)), strengthening R9.3.6's "up-to-date, signed
  permit version" beyond identity/validity into a fuller processing/handover instruction. Both are
  fixed at issuance and — as of this snapshot — only ever re-selectable when an amendment is
  approved (the output controller can be swapped for a new one; the researcher, being
  application-derived, is always carried forward unchanged): there is no longer any route to
  add/remove an authorised person ad hoc on an existing permit version, closing a version-integrity
  gap the previous ad-hoc "Authorised persons" panel left open (every `AuthorizedPerson` row that
  exists is now always part of some version's signature).

  Remaining gap:
  - **R9.3.6 transmission.** The signed permit document is available for download, not
    proactively pushed to the data user, data holder, or SPE provider.
- **§9.4 After a decision — ◑.** Amendment and renewal requests are documented, decided, and (on
  approval) issue a new permit version (R9.4.1–9.4.7), via `PermitChangeRequest`.

### §10 — Decision appeals: ✅ (100%, 3/3)
A real, working `Appeal` model + workflow, not just a bare record — `AppealsPanel.tsx` registers an
appeal (appellant, grounds, handling authority) and drives it through
SUBMITTED→UNDER_REVIEW→UPHELD/REJECTED/WITHDRAWN, with a `decisionSummary` recorded on close. This
is DAAMS integrating the appeal mechanism as a workflow, the R10.0.4 option (MAY, not scored).
Works identically for national and HD@EU-sourced applications — no type/source restriction found in
`appeals/route.ts` — so R10.0.2's "applies to both application types" holds; not itself a scored
MUST item either way.

Out of scope: R10.0.1 (Member States creating national appeal procedures) — a legal/organisational
obligation, not a DAAMS requirement; see the methodology note above.

All three scored requirements now covered:
- **R10.0.3** — the existing "RECHTSMIDDELEN" section in `generate-decision-pdf.ts` (an objection
  and appeal can be filed per the Awb) now states the concrete 6-week deadline computed from the
  decision date and the submission channel (`info@hdab.nl`, the same contact already used in the
  permit PDF).
- **R10.0.5** — `Attachment` gained an optional `appealId`; `POST /api/appeals/[id]/attachments`
  lets staff attach correspondence/documents to an appeal (the appellant's written objection, a
  court ruling, etc.), served back through the existing generic `GET /api/attachments/[id]` route.
- **R10.0.6** — `signAppealDecision`/`generate-appeal-decision-pdf.ts` (mirroring
  `signDecisionCard`/`generate-decision-pdf.ts`) produce a real Ed25519-signed PDF once an appeal
  reaches a terminal decision (UPHELD or REJECTED — both equally final, unlike the decision card's
  positive/negative asymmetry), served via `GET /api/appeals/[id]/pdf`.

### §11 — Mutual recognition: ✗ not implemented
Fetching already-issued data permits from the central registry to display to HDAB personnel
(R11.0.1) is absent. Spec severity: **MAY**.

### §12 — Trusted data holders (TDH): ✗ not implemented
The simplified-assessment TDH workflow (refer application to a TDH, TDH records assessment +
proposed decision, HDAB accepts/rejects) is absent (R12.0.1–12.0.3). Spec severity: **MAY**, but a
GUI implementation carries MUST sub-requirements — R12.0.2's bundle (visual assessment workflow,
transfer/controlled access to the referred application, TDH recording an assessment against Art.
68(1)/(2) or Art. 69(2)/(3), TDH submitting a proposed decision, HDAB formally accepting/rejecting
it) is entirely unbuilt. Corresponds to EHDS Art. 72.

A small, related building block now exists but should not be read as partial coverage of this
section: `DataHolder.isTrusted` (a registry flag, settable in Reference data) and
`Application.trustedDataHolderId` (a selector on the application, staff-only) let a case handler
record which trusted data holder is involved with a given application. This is groundwork — "is
this data holder TDH-eligible, and is one associated with this case" — not an implementation of
any R12.0.1/12.0.2 requirement: there's no referral, no TDH-side view or access to the
application, no assessment recording, and no proposed-decision accept/reject step. Kept as ✗
above rather than upgraded, since none of the actual MUST bundle is touched.

### §13 — Interaction with secure processing environments: ✅ (100%, 2/2) / re-scope
v0.5 places SPE **operations** (creation, decommissioning) **outside** D6.4, in deliverable
**D7.4**. The DAAMS's role is limited to (a) handover of permit info to the SPE — permit id +
version, authorised persons, validity, changes — and (b) recording lifecycle events for an
auditable application↔permit↔SPE link (R13.0.1–13.0.2). The app instead models the SPE
**environment** lifecycle (`SpeProvisioningOrder`: REQUESTED→ACTIVE→DECOMMISSIONED), which is now
out of DAAMS scope; the in-scope part (permit-info handover + audit link) is fully present via the
permit, authorised persons and logs.

R13.0.1 requires the permit information "needed by the designated **SPE or SPE operator**" (exact
spec wording) to be handed over or structurally available — the SPE operator is *selected* on the
application, during the fee-estimate step (Art. 62(5)), and its `speOperatorId` is then
*propagated* to the permit at issuance (still editable via an AMENDMENT change request; carried
forward unchanged on renewal/revocation appeal). The SPE *provider* is deliberately never stored
redundantly — it's derived via `speOperator.speProvider` at read time, so it can't drift out of
sync with the reference-data registry. Both are part of the **signed** canonical payload
(`SignablePermit.speOperator`, `canonicalPermitPayload` in
[permit-signing.ts](../src/lib/permit-signing.ts)) — not just the staff-facing permit page — so
R13.0.1's "structured availability... needed by the designated SPE or SPE operator" is met by the
one document actually meant to be consumed externally
(`GET /api/permits/[id]/json`). Every amendment that changes the designated operator is logged via
`DataPermitLog` (R13.0.2's auditable-link requirement).

R13.0.1 also names **authorised persons** explicitly as part of what's handed over — this is now
role-differentiated (RESEARCHER / OUTPUT_CONTROLLER, the latter being D6.3's four-eyes check on
SPE output) and carries a sample DID identity per person, rather than a flat name list; see §9.3
above for the full detail. Both roles are fixed at issuance and only re-selectable on an approved
amendment, matching the same "carried forward unchanged unless an amendment changes it" discipline
already described for `speOperatorId` here.

### §14 — DAAMS within national EHDS IT infrastructure: ◑ partially real
The design constraint that DAAMS **MUST NOT** communicate directly with the Central Platform
(R14.0.1) is respected. Queue retrieval and decision-card transmission ([ncp-client.ts](../src/lib/ncp-client.ts))
now call the real **National Dispatcher OpenAPI** on the HDAB-NL test environment
(`https://ap.hdab-nl.eu/national-dispatcher/{queue,decision-cards}`, R14.0.2/14.0.3) when
`NCP_API_KEY` is configured, falling back to fixed sample data otherwise. Still missing:
queue/retry/logging of failed exchanges (R14.0.4) — a failed call is caught and silently
substituted, not retried or logged for follow-up — and any interoperability test suite against
the NCP (R14.0.5).

## 3. On the term "decision card"

It is **not a UI element**. Per §9.2 it is "the structured format in which decision information is
communicated to applicants via the HealthData@EU Central Platform" — i.e. a standardised
**message/record** (defined against the National Dispatcher OpenAPI) that is materialised as a
document (an unsigned pre-permit PDF for a positive decision; a signed PDF for a negative one). It
is an interoperability construct, closer to a DTO than a screen.
