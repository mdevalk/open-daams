# D6.4 v0.5 — full requirements matrix (MUST / SHOULD / MAY)

_Snapshot date: 2026-08-20._

Every individually numbered (`R<section>.<subsection>.<n>`) requirement in **TEHDAS2 D6.4 —
DAAMS Technical specification, v0.5 (24 March 2026)**, in document order, each with its RFC 2119
level and a description of how (or whether) open-daams implements it. **188 requirements** in
total, extracted directly from the source PDF text (`pdftotext -layout`, cross-checked against the
rendered pages) — one requirement, `R7.4.2`, is duplicated in the source document itself (two
different requirements both carry that id); both are listed below, distinguished as (a)/(b).

This is the **flat, complete list** — companion to [`d6.4-gap-analysis.md`](./d6.4-gap-analysis.md),
which reads section-by-section with coverage percentages and longer prose explanations. Where a
requirement's implementation note here is terse, the gap-analysis doc usually has the fuller story;
this document exists so every individual requirement — not just the ones significant enough for
gap-analysis prose — has its own row. Requirement text below is **paraphrased for length**, not a
verbatim quote; the source PDF is the authoritative wording. §15/§16 (non-functional and security
requirements) are **not** covered in `d6.4-gap-analysis.md` at all — those two sections' assessment
here is new, cross-referenced against `docs/owasp-top10-assessment.md`, `docs/wcag-2.1-assessment.md`,
and `docs/nis2-assessment.md`.

> **Legend:** ✅ implemented · ◑ partial · ✗ not implemented · ⏳ blocked on an external dependency ·
> — out of scope or not code-assessable (legal/organisational obligation, infrastructure/deployment
> concern, or requires a real external system this project can't stand up alone). This is an
> unofficial community project; nothing here is compliance advice.

## Method

Requirement text and IDs were extracted from the official D6.4 v0.5 PDF via `pdftotext -layout`,
parsed programmatically (every `R\d+\.\d+\.\d+`-prefixed paragraph), and spot-checked against the
rendered pages for extraction artifacts. Implementation status for §6–§14 is drawn from the existing,
independently-verified [`d6.4-gap-analysis.md`](./d6.4-gap-analysis.md) (itself built from direct
PDF reads and live code/DB verification across many passes — see that doc's own revision history).
§15–§16 status is freshly assessed this pass by reading the relevant source (`src/lib/authz.ts`,
the `Contact`/`AuditLog`/`AuthzFailureLog`/`ApplicationLog`/`DataPermitLog` models, `src/proxy.ts`,
`src/lib/ncp-client.ts`, Prisma's `DateTime` handling) and cross-referencing the three existing
security/accessibility assessment docs, which had already done deeper, live-tested work covering
much of this ground under a different lens (OWASP Top 10, WCAG 2.1, NIS2).

## §6 — Front office (applicant): out of DAAMS scope

**All 48 requirements below are out of scope for this project.** D6.4 §6 defines the
**applicant-facing front office** (submission UI, applicant portal/login, document upload,
notifications, dataset browsing/selection) — per this project's own scope (`CLAUDE.md`), that's the
**central platform's / WP6's** responsibility, not the back-office DAAMS open-daams implements.
open-daams ships a staff-facing application form/list/submit/withdraw/fee-estimate as a practical
demo stand-in so the back-office workflow can be shown end-to-end, but this is a convenience shim,
not an R6.x implementation: no applicant login/portal (an "acting as" role switcher stands in), no
document upload (`Document` stays a metadata stub), no applicant-facing notifications, no draft
editing/clone/print/import, datasets are free-typed rather than picked from a real catalogue. See
`d6.4-gap-analysis.md` §6 for the full framing.

## Summary

Across all 188 requirements: 34 MUST + 14 SHOULD/MAY in §6 (48 total) are out of open-daams's
declared scope (front office); a further handful (R10.0.1, R15.1.6, R15.5.5, R15.7.1, R15.7.3,
R16.0.2/16.0.3) are legal/organisational/deployment concerns not assessable by reading application
code. Of the remainder, the back-office core (§7–§10, §13) is largely built and matches
`d6.4-gap-analysis.md`'s section-level percentages; §11/§12 (mutual recognition, trusted data
holders) are genuinely unbuilt MAY-level features; §14's cross-border resilience (retry/logging of
failed NCP exchanges, an interoperability test suite) is the clearest MUST-level gap outside the
scope exclusions. §15/§16's non-functional requirements surface the project's own accepted
baseline plainly: audit logging is comprehensive and was recently hardened (OWASP A09), but real
authentication/eIDAS (R15.5.1/R15.5.2), tamper-evident log integrity (R15.4.1/15.4.5), operational
monitoring (R15.4.6/15.4.7), and performance/availability engineering (§15.3) are all unbuilt —
consistent with this being a reference implementation over test data, not a production HDAB
deployment.
